# D1: Lock rows

State: ready for review
Branch: worktree-d1-lock-rows

Delegated by the lead after F5's finding 2: the device layer's room check took a stored row's type from the wrong
table, so it never found the rows of locks made by hand.

## Findings (stock OS 1.74, in analog-emu)

Measured by `tools/tests/12-lock-rows.sh`: on the default pattern, a lock through stock's lock set (0x400c058c) on
step 0 for each sound index 0..41, on BD (fine flag 0), MT (fine 1) and the FX track (fine 0 and 1), recording the
rows that appear and whether they go after the clear. 168 cases; the table is written to
`build/emu/12-lock-rows/map.txt` on each run.

1. **The voice tracks' map is the int32 table 0x401c5c7c**, not 0x401c5be4. FLTR DEC / FRQ / RES (27, 30, 31) give
   18, 20, 21, as F5 measured. It is a permutation of 0..41: no two sound indexes share a type on a voice track.
   BD and MT give the same map. The default pattern's own rows (tracks 2–5) agree with it.
2. **0x401c5be4 is the FX track's type → index table.** 0x401c5b4c, the "inverse" the 0.4 notes named, is the FX
   track's index → type table (38 entries). The voice pair is 0x401c5c7c / 0x401c5d24. The selector is the
   routine 0x400075c8 / 0x40007602 (track, index): FX = track 12.
3. **The FX track stores rows too** (track 12), types from 0x401c5b4c. For indexes 38..41 stock reads on past that
   table's 38 entries into 0x401c5be4[0..3]: types 9..12, shared with indexes 18..21. The routine 0x40007602 gives
   0 there, so the row code does not use it; the device layer reads the tables.
4. **A fine lock takes two rows:** (type, track), then a row of type and track 0x80. Confirms the cost of 2 the
   room check already used.
5. **Rows follow the locks a tick later.** The lock set posts a notice; stock makes the row by the next `ev_tick`
   and frees it by the next tick after the last lock of its type on the track is cleared. Nothing changes in the
   row table during the lock set call itself.
6. **Stock past its limit** (71 rows used, a lock set with no room check): the lock is set, no row is made, no
   warning. SAVE PATTERN + RELOAD PATTERN and a power cycle keep it (the control, a lock set after the save, is
   gone after the reload). So the firmware notes' "past that a new lock lives only until the next save" is wrong
   for pattern save / reload. Where a rowless lock is lost is not established (see open points).
7. **Words 42–43 of a step's 88 lock bytes** are the step's count of locks (int32), rewritten by 0x400ac646 after
   every lock set / clear.
8. **The default pattern A01 is not empty:** tracks 2–5 hold locks, 15 rows in use, four of them fine.

`docs/firmware-notes-os174.md` section 4 is corrected accordingly.

## Open points

- **Where a lock without a row is lost.** Not by pattern save / reload or a power cycle (finding 6). The likely
  places are SAVE PROJECT + LOAD PROJECT (the project file) and a pattern SysEx dump. A probe saved the project
  with a rowless lock and loaded it back; the emulator did not finish the load (one dtboot run of 3 G
  instructions still running after 74 minutes; stopped). Until this is measured, the 71-row limit the room check
  enforces rests on the row counts, not on an observed loss.
- **Rows lag a tick.** Within one key handler (the audition's restore followed by the next take's write) the room
  check sees the rows as they were before the restore: rows of locks the restore cleared still count, rows of
  locks it re-set are not there yet and count as new. Both err towards refusing, so I8 holds; near the limit a
  take may be refused that would fit. A restore re-sets locks through stock with no room check, so if the take in
  between used up the room, a restored lock can end without a row (it is still kept by pattern save, finding 6).
- Measured on BD, MT and FX; the other voice tracks are assumed to use the same map (stock selects the table by
  "track == 12" only, routine 0x400075c8).
