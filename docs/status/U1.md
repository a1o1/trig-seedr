# U1: a safe mods' area on the Syntakt

State: ready for review
Branch: worktree-u1-memory-st (from e6291d3)

## Done

- **A range Syntakt OS 1.42 never uses:** `0x478af2ca`–`0x47c00000` (about 3.3 MiB). Evidence below; the canary
  covers `0x478b0000`–`0x47c00000`.
- **`tools/st_build.sh`**: the mods' area is `ST_AREA` (hex `LO-HI`), set on the Syntakt profile in the patch step
  as the flash limit already is. **Default `47a00000-47b00000`** (1 MiB inside the range: about 1.4 MiB above the
  DSP boot buffer, 1 MiB below the DMA ring). `ST_AREA=46000000-46010000` builds in Synfact's area as before.
  seedr links there with **983,876 bytes spare** (core 456 + `.run` 53,788 + `.bss` 10,420).
- **`tools/st_u1.sh`**: the canary, 6 PASS (about 2.5 minutes), below.
- **analog-emu-st**: `dtboot --fill LO-HI=PAT` (before the run, `PAT ^ address` in every word) and `--check-fill
  LO-HI=PAT` (after it, the words changed): commit `19571f6` on the local branch `syntakt-modified`, not pushed.
- **The Syntakt checks with every build in the new area** (default `ST_AREA`): `st_run_tests.sh` 01 8, 13 21, 14 18,
  15 4, 41 13, 43 15, 44 17 PASS; `st_s3.sh` 18, `st_s3b.sh` 28, `st_s2.sh` 10, `st_s03.sh` 9 PASS (core-st now links
  in the 1 MiB area: 979,360 bytes spare). **03-save: 4 PASS, 2 FAIL**, the same with `ST_AREA=46000000-46010000`:
  its power-cycle part assumes analog-emu's power off saves nothing on the Syntakt, and analog-emu-st's
  `syntakt-modified` now has U2's supercap model (`5c970d9`): the power off writes 8,000 sectors and a valid state
  slot, so the cold boot shows the take. Not the area; 03-save needs updating for the new model (U2's or the lead's).

## Findings

The DDR map above the OS's reset clear, OS 1.42:

|---|---|---|

| `0x47c00000`–`0x48000000` | a 4 MiB DMA ring (cleared by `0x4009673c`: `bzero(0x4fc00000, 0x400000)`, eDMA TCDs at `0xfc0455xx`, offsets masked `0x7ffff × 8`); the reset stack starts at `0x48000000` (`0x400004f2`) | [inferred: code]; [measured: the control's first 64 KiB cleared at boot] |

Why nothing uses `0x478af2ca`–`0x47c00000`:

- **No code operand points into it** [inferred]. A disassembly sweep of the main OS (1,096,150 instructions,
  capstone, with data skipped) finds operands in the range and its uncached view only in data decoded as
  instructions (above `0x401d0400`, where code ends; `rts` density per 64 KiB) and in two places in code: `0x4f9db22d`
  at `0x400984a4` and `0x40098b7c`, both ColdFire MAC coefficients (the register is a MAC operand and is overwritten
  before any access), like the `#$3f80` and `#$0fc04000` next to them. The SRAM code (`0x4033a000`–`0x40348b90`) has
  none. `0x47efffff:e0000000` (`0x40158906`) is `FLT_MAX` as a double; `0x47c35000` is the float 100000.
- **Nothing runs into it** [inferred]: the blob's bound (above) ends below the DSP buffer; the heap is inside the
  reset clear; the DMA ring starts at its top.
- **The canary** [measured, analog-emu-st]: `0x478b0000`–`0x47c00000` filled before a cold boot of stock 1.42 on a new
  card, unchanged after the boot; after a session (TRIG pages, SYN, FLTR, AMP, LFO, FX, track change, MENU, arrows,
  four knobs, grid-recording edits on 9 steps, PLAY with three pattern changes); after a project save (FUNC + GLOBAL)
  and LOAD PROJECT with PLAY; after a power off and a cold boot on that card (filled again), LOAD PROJECT 002 ("LOAD
  OK"), PLAY. The controls show the probe sees the OS's writes: at the cold boot the DSP buffer's words change
  (95,943 of 98,305) and the ring's first 64 KiB is cleared (16,384 of 16,384). analog-emu has no cache model by
  default, so a store is in memory at once.

## Not shown

- **Samples.** The canary ran with no samples on the card: analog-emu-st cannot load the 64 slots. The blob's bound
  is from the code, not measured.
- **A unit.** The emulator's DDR is a model. The equivalent of elekloader's unit canary (`ddr-canary-a4mk2`) is not
  run.
- Code that computes an address in the range from a base outside it (no literal) would not show in the operand scan;
  the canary covers what the session exercises.

## Room in the 64 KiB area (if the new area is not adopted)

Not done: with the new area, 983,876 bytes are spare, so moving data to the heap gains nothing there and would
change code the Rytm shares. In Synfact's 64 KiB area (836 bytes spare) the largest movable items are preview.c's
`work` (4,120), `was` (1,384) and `pv_out` (1,030), and the recipe store `recipe` (2,880). preview.c is its own
translation unit (it needs an attach of its own, not `SD_FRAME_HEAP`), and the Syntakt tests read and poke
`recipe[...]` by symbol, so moving it needs `tools/emu.sh`'s `emu_addr` to follow a pointer.
